# i18n

This app serves more than one language. The plugin is contained in these files:

| File                                          | Owns                                                   |
| --------------------------------------------- | ------------------------------------------------------ |
| `src/lib/i18n/config.ts`                      | Locale list, default, path split/build, hreflang set   |
| `src/lib/i18n/messages.ts`                    | Typed message catalog and `t(locale, key)`             |
| `server/middleware/locale.ts`                 | The decision, the cookie, the redirect for bare paths  |
| `src/routing/rules.ts` → `localePrefixes`     | Rewrites that strip `/tr`, `/en` before route matching |
| `src/components/layout/language-switcher.tsx` | The switcher — plain links, no JavaScript              |

## The URL carries the locale, except for the default one

```
/catalog      default language, no redirect
/en/catalog   English
/tr/catalog   308 → /catalog   (one page never gets two addresses)
```

The default language owns the bare path, so adding a language moves no existing URL. The rewrite
strips the other prefixes before matching, so **routes are written once, without a locale segment**.
The browser-visible path keeps its prefix, and that is what canonical URLs, hreflang and cache keys
use.

There is no `Accept-Language` redirect, on purpose: it would make the canonical URL answer
differently per visitor — uncacheable, and a reliable way to get the wrong language indexed. The
switcher is how a visitor changes language.

## Reading the locale

```ts
import { pageLocale } from "~/lib/i18n/config";

loader: async (ctx) => ({ data: { locale: pageLocale(ctx), … } }),
```

`pageLocale(ctx)` reads the middleware's decision (`ctx.values.locale`), not the URL. Everything
reads the same value that way — including the cache key, which the platform fragments automatically
because the middleware published it.

Never parse the locale out of `ctx.url` yourself in a page: two sources of truth is how a page ends
up rendered in one language and cached under another.

## Adding a locale

1. `LOCALES` in `src/lib/i18n/config.ts`.
2. A catalog with the same keys in `src/lib/i18n/messages.ts` — a missing key fails the typecheck.
3. A `localePrefixes` entry in `src/routing/rules.ts`.
4. `pnpm ci`.

Each locale multiplies the cache entries of every cached page. Two languages doubles them.

## Translating

UI chrome goes in the catalog through `t(locale, key)`. Content — product names, articles, prices —
does not: the gateway returns it already translated. `server/services/menu.ts` is the worked example
— it reads the `x-locale` header the middleware injects, asks the gateway with `?locale=`, and puts
the locale in its **cache key**. That last part is not optional: an upstream cache without the locale
in its key serves the first language that warmed it to everyone else.

## Metadata

`server/product/document-shell.ts` gives every page `<html lang>` and a full hreflang set (all
locales plus `x-default`). A route that needs its own alternates can return `languageAlternates` from
`generateMetadata`; the shell only fills in what the route left empty.

A one-sided hreflang set is worse than none — search engines read the translations as separate pages
competing with each other.

## Links

Use `<Link href="/catalog">` from `~/components/link` for every internal link. It prefixes the path
with the locale of the page being rendered, read from context the layout provides.

A raw `<a href="/catalog">` is the bug this plugin is most likely to grow: the switcher takes the
visitor to `/en/catalog` and the first raw link takes them back to Turkish. `localeHref` deliberately
leaves `/api/*`, absolute URLs, `//host` and `#fragment` alone; a bare `?page=2` needs no prefix
because it stays on the current path.

Islands are separate React roots and do not see the context — hand an island the locale as a prop.
