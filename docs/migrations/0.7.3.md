# 0.7.3: her gateway çağrısı kimlik taşır, cache'siz sayfa

Tür: yeni bir çağrı kontratı ve bir örnek sayfa. Mevcut uygulamalar için kırıcı değişiklik yok —
`gatewayFetch` ve `gatewayFetchForRequest` olduğu gibi duruyor.

## Sorun

Ziyaretçinin tracking id'si, client IP'si ve cihaz tipi backend'in her istekte görmesi gereken
şeylerdi, ama bunları taşımak her servis fonksiyonunun kendi işiydi. Böyle bir kural on sekiz yerde
elle uygulanır, on dokuzuncuda uygulanmaz — ve unutulduğu yer sessizdir: istek başarılı olur,
yalnızca gateway kimin sorduğunu bilmez.

## Kontrat

`@originloom/core/adapters/gateway-identity`:

```ts
export type GatewayIdentity = { userTrackingId?: string; clientIp?: string; deviceType: string };

readGatewayIdentity(request); // istekten okur
applyGatewayIdentity(headers, identity); // giden header'lara uygular
configureGatewayIdentityHeaders({ userTrackingId: "X-Visitor-Id" }); // isim değiştirir
```

Üç değerin hiçbiri çağıranın gönderdiği bir header'dan gelmez: tracking id session step'in yazdığı
cookie'den, client IP platformun trusted-proxy zincirinden çözdüğü adresten, cihaz User-Agent'tan.
Sonucu iki yönlü: bir servis bunları geçirmeyi **unutamaz**, bir client `x-user-tracking-id` set
ederek başkasıymış gibi **konuşamaz**. İkincisinin testi var
(`apps/showroom/tests/server/gateway-identity.test.ts` → "ignores an identity header the caller tried
to supply").

Varsayılan header adları `x-user-tracking-id`, `x-client-ip`, `x-device-type`. Gateway'iniz farklı
adlar bekliyorsa `configureGatewayIdentityHeaders()` ile başlangıçta bir kez ayarlayın; çağrı
yerlerinde tekrarlanmaz.

## Üç fonksiyon

| Fonksiyon                                 | Kimlik | `Authorization` | Nerede                              |
| ----------------------------------------- | ------ | --------------- | ----------------------------------- |
| `gatewayFetchWithIdentity(request, path)` | ✓      | ✗               | **Varsayılan** — servislerin çoğu   |
| `gatewayFetchForRequest(request, path)`   | ✓      | ✓               | BFF uçları, `neverCache` route'lar  |
| `gatewayFetch(path)`                      | ✗      | ✗               | İsteği olmayan işler (kuyruk, cron) |

`gatewayFetchWithIdentity` bu sürümde yeni ve varsayılan olan o. `gatewayFetchForRequest` artık
kimliği de ekliyor — davranış genişledi, kırılmadı.

Kimlik **telemetri ve güvenlik bağlamıdır, içerik boyutu değildir.** Cache key'i bu değerleri
içermez ve içermemelidir: tracking id ziyaretçi başına bir cache entry demektir. Gateway cevabını bu
değerlere göre değiştiriyorsa o cevap paylaşımlı cache'lenen HTML'e giremez.

## Servisler `signal` değil `Request` alır

Kimliğin gateway'e ulaşmasının yolu bu:

```diff
-export async function listItems(page: number, perPage: number, signal: AbortSignal) {
-  const response = await gatewayFetch(`/items?page=${page}`, { signal });
+export async function listItems(page: number, perPage: number, request: Request) {
+  const response = await gatewayFetchWithIdentity(request, `/items?page=${page}`);
```

`Request` hem iptal sinyalini hem kimliği taşır; `signal` yalnız yarısını. Çağrı yerinde
`ctx.request.signal` yerine `ctx.request` geçirmek yeterli. `SeoRoutesOptions.entries` de aynı
nedenle `(request: Request)` alıyor (önce `(signal: AbortSignal)` idi) — sitemap üretimi de bir
istektir.

## Kuralı koruyan test

Üretilen uygulama `tests/gateway-identity.test.ts` ile geliyor: `server/` altında ham `gatewayFetch`
kullanan her dosyayı bulur ve gerekçesiyle listelenmemişse testi düşürür. Kural bir konvansiyon
değil, kırılabilir bir şey oluyor.

Showroom'a eklenirken bu test gözden kaçmış iki çağrıyı hemen yakaladı; biri gerçek bir bulguydu:
cihaza göre paylaşımlı cache'lenen menü `gatewayFetchForRequest` ile çağrılıyordu, yani çağıranın
`Authorization`'ını taşıyordu. Paylaşımlı cache'e giren bir cevabın asla yapmaması gereken şey.

## Cache'siz sayfa

Üretilen uygulamada yeni bir `/no-cache` sayfası var: ne doküman cache'i ne de upstream veri cache'i.
Her istek bir gateway round trip'i demek, ve sayfa render zamanını, gateway süresini ve `x-cache`
durumunu ekrana yazıyor. `/catalog` (HTML cache) ve `/data-cache` (veri cache'i) ile yan yana
yenilendiğinde aradaki fark cache katmanının tüm gerekçesi.

`robots: { index: false, follow: false }` ile geliyor — istek başına upstream çağrısına mal olan bir
sayfanın üzerinde crawler dolaşmamalı.
